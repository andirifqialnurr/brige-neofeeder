# Backup, restore verification, and upload retention

## Database backup

`docker compose exec backend php artisan bridge:backup`

Creates a private SQL file and SHA-256 JSON manifest under
`storage/app/private/backups` on the persistent backend-storage volume. A failed
dump does not produce a completed SQL file. The dump uses a consistent InnoDB
snapshot and does not put passwords in command arguments. The backend image
includes the MySQL client; rebuild it before using the command.

Copy the SQL and manifest to separate protected storage. A copy on the same VPS
is insufficient for host loss. Keep `APP_KEY` and environment secrets in a
separate protected backup: restoring the database alone cannot decrypt credentials.
Uploaded workbooks are outside this database dump and need their own storage backup.

For native development, set `MYSQLDUMP_BINARY` and `MYSQL_BINARY` to the installed
MySQL client executables. Test compatibility with the actual database version.

## Restore drill

Configure a **separate disposable MySQL service**, without application workers:

```env
RESTORE_MYSQL_HOST=restore-mysql
RESTORE_MYSQL_PORT=3306
RESTORE_MYSQL_USER=root
RESTORE_MYSQL_PASSWORD=your-test-service-password
```

Run `php artisan bridge:backup --verify=/absolute/path/to/backup.sql` inside the
backend runtime. Use a trusted backup generated by this application. The command
checks the manifest, creates a random `bridge_restore_<uuid>` database, imports
the dump, verifies core tables, reports row counts, then drops only that temporary
database. It refuses an unconfigured restore target or the same host/port as the
application; do not configure aliases pointing back to the application server.
No app/worker is started on restored data, and no Neo Feeder request is made.

Scheduling, external backup transfer, and a production restore remain operator
deployment work. These commands do not automatically change production schedules.

## Upload retention

```bash
php artisan bridge:prune-import-files --days=90
php artisan bridge:prune-import-files --days=90 --apply
```

The first command is a preview. `--apply` deletes eligible workbook files only;
staging, findings, attempts, and audit history remain. Eligibility requires an
Excel batch that has been `synced` or `failed` and unchanged for the chosen age.
Active, ambiguous, or retryable attempts prevent deletion. In-progress/invalid
batches are retained for operator work. Paths must belong to that tenant's imports
directory. The policy is disabled by default (`UPLOAD_RETENTION_DAYS=0`); no
destructive scheduler is installed automatically.

## Local verification — 2026-09-15

MySQL 8.4.3 source and restore services used separate data directories and ports.
`bun run test:integration --with-backup` passed **6 tests / 73 assertions** including
the delivery suite, actual dump/import, restored core-table row counts, checksum
tampering rejection, and refusal to restore on the application host/port.
Set the `RESTORE_MYSQL_*` and client executable variables before this extended run.
Retention tests passed **2 tests / 12 assertions**. Docker image build and VPS
backup scheduling/external transfer have not been exercised in this environment.
